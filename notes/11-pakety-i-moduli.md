# Конспект 11. Пакеты, модули, видимость имён

## 1. Пакет — единица организации кода

Каждый `.go`-файл принадлежит ровно одному пакету, указанному в первой строке файла. Один пакет может состоять из нескольких файлов в одной папке — все они делят общее пространство имён.

```go
// файл math_utils/add.go
package mathutils

func Add(a, b int) int { return a + b }
```

```go
// файл math_utils/subtract.go
package mathutils

func Subtract(a, b int) int { return a - b } // видит Add из другого файла того же пакета без импорта
```

**Правило:** все файлы в одной папке обязаны иметь одинаковое имя пакета (кроме специальных файлов `_test.go`, где допустим суффикс `_test`, и специальных build-файлов).

## 2. Импорт пакетов

```go
import (
    "fmt"                                      // стандартная библиотека
    "strings"                                  // стандартная библиотека

    "github.com/username/myproject/internal/service" // локальный пакет проекта
    "github.com/gorilla/mux"                    // внешняя зависимость
)
```

Импортированный пакет используется через его имя (обычно совпадает с последней частью пути, но может быть переопределено в объявлении `package`):

```go
result := mathutils.Add(2, 3)
```

### Псевдонимы импорта (import alias)

```go
import (
    m "github.com/username/myproject/internal/mathutils" // теперь обращаемся через m.Add(...)
    _ "github.com/lib/pq"                                  // импорт только ради побочных эффектов (init())
)
```

`_` перед импортом — специальный "пустой идентификатор": пакет импортируется (его `init()`-функции выполняются), но напрямую по имени не используется. Классический пример — регистрация драйвера базы данных.

## 3. Видимость имён (экспорт) — напоминание и расширение

С большой буквы — экспортируется из пакета, с маленькой — доступно только внутри пакета. Это правило действует одинаково для:

```go
package service

type User struct {   // экспортируемый тип
    Name string        // экспортируемое поле
    age  int            // НЕ экспортируется — доступно только внутри пакета service
}

func NewUser(name string, age int) *User { // экспортируемая функция
    return &User{Name: name, age: validateAge(age)}
}

func validateAge(age int) int { // НЕ экспортируется — вспомогательная внутренняя функция
    if age < 0 {
        return 0
    }
    return age
}
```

Снаружи пакета `service` можно создать пользователя только через `NewUser` и прочитать/изменить `Name`, но нельзя напрямую тронуть `age` — классический способ инкапсуляции без ключевых слов `private`/`public`.

## 4. internal — специальная защищённая папка

```
myproject/
├── internal/
│   └── billing/
│       └── billing.go   // package billing
└── cmd/
    └── api/
        └── main.go
```

Любой пакет внутри `internal/` может быть импортирован **только** кодом, который находится в поддереве того же родителя, что и сама папка `internal`. Это проверяется компилятором, а не просто соглашением — попытка импортировать `internal`-пакет из другого модуля приведёт к ошибке компиляции.

## 5. init() — функция инициализации пакета

```go
package config

var settings map[string]string

func init() {
    settings = make(map[string]string)
    settings["env"] = "production"
    // выполнится автоматически при первом импорте пакета, ДО main()
}
```

`init()` может быть несколько в одном пакете и даже в одном файле — выполняются в порядке объявления. Используется редко и только когда действительно нужна инициализация до старта программы (регистрация драйверов, парсинг встроенных данных) — злоупотребление `init()` считается плохой практикой, так как скрывает логику инициализации от читателя `main()`.

## 6. go.mod и go.sum подробнее

```go
module github.com/username/myproject

go 1.21

require (
    github.com/gin-gonic/gin v1.9.1
    github.com/stretchr/testify v1.8.4
)

require (
    // косвенные зависимости (зависимости твоих зависимостей) — Go помечает их автоматически
    github.com/bytedance/sonic v1.9.1 // indirect
)
```

`go.sum` содержит криптографические хэши каждой версии каждой зависимости (и прямой, и косвенной) — это защита от подмены пакета (supply chain attack): если кто-то скомпрометирует пакет на сервере, хэш не совпадёт, и `go build` откажется собирать проект.

**Полезные команды:**

```bash
go get github.com/gin-gonic/gin@v1.9.1   # добавить/обновить конкретную версию
go get github.com/gin-gonic/gin@latest    # обновить до последней
go mod tidy                                 # привести go.mod/go.sum в соответствие с реальными импортами
go mod why github.com/some/pkg              # почему эта зависимость вообще в проекте
go mod graph                                # граф зависимостей
go list -m all                              # список всех зависимостей модуля
```

## 7. Семантическое версионирование (semver)

Версии зависимостей вида `v1.9.1` следуют формату `vMAJOR.MINOR.PATCH`:
- **MAJOR** — несовместимые изменения API (обновление вручную, с проверкой breaking changes).
- **MINOR** — новая функциональность с обратной совместимостью.
- **PATCH** — исправления багов без изменения API.

Важная особенность Go Modules: при MAJOR-версии 2 и выше путь импорта модуля обязан включать версию, например `github.com/user/lib/v2` — это позволяет одной программе одновременно использовать v1 и v2 одной библиотеки как формально разные пакеты.
