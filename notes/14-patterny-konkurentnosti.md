# Конспект 14. Паттерны конкурентности и типичные ошибки

## 1. Race condition (гонка данных) — что это и как найти

Гонка данных возникает, когда две горутины обращаются к одной переменной одновременно, и хотя бы одно обращение — запись, без синхронизации.

```go
// БАГ:
counter := 0
var wg sync.WaitGroup
for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        counter++ // ГОНКА: чтение+инкремент+запись не атомарны
    }()
}
wg.Wait()
fmt.Println(counter) // почти никогда не будет 1000
```

**Инструмент для поиска гонок — встроенный race detector:**

```bash
go run -race main.go
go test -race ./...
```

Race detector замедляет выполнение в разы, но точно находит гонки во время выполнения кода, покрытого тестами/сценарием запуска. На собеседовании часто спрашивают именно про флаг `-race` — это стандартный инструмент в CI любого серьёзного Go-проекта.

**Исправление** — либо мьютекс, либо атомарные операции из пакета `sync/atomic`:

```go
import "sync/atomic"

var counter int64
// ...
atomic.AddInt64(&counter, 1)
// ...
fmt.Println(atomic.LoadInt64(&counter))
```

`sync/atomic` быстрее мьютекса для простых операций (инкремент, сравнение-и-обмен) над одиночными числами, но не подходит для защиты сложных структур данных из нескольких полей — там нужен `Mutex`.

## 2. Deadlock (взаимная блокировка)

Классический пример — две горутины ждут друг друга бесконечно:

```go
// БАГ — main зависнет навсегда:
ch := make(chan int) // небуферизованный!
ch <- 1               // main блокируется на отправке, но НИКТО не читает
fmt.Println(<-ch)     // эта строка никогда не выполнится
```

Go умеет детектировать **некоторые** простейшие дедлоки во время выполнения (когда вся программа "зависла" и не осталось живых горутин) и завершает программу с `fatal error: all goroutines are asleep - deadlock!`. Но это работает не всегда — например, если хотя бы одна горутина жива (пусть и тоже застряла в ожидании), рантайм не всегда сможет это распознать мгновенно.

**Классический дедлок с двумя мьютексами (lock ordering problem):**

```go
var mu1, mu2 sync.Mutex

// горутина A:
mu1.Lock()
mu2.Lock() // если горутина B в этот момент держит mu2 и ждёт mu1 — ДЕДЛОК

// горутина B:
mu2.Lock()
mu1.Lock()
```

**Правило избежания:** всегда захватывать несколько мьютексов **в одном и том же порядке** во всех местах кода.

## 3. Утечка горутин (goroutine leak)

Горутина, которая никогда не завершится (например, ждёт на канале, в который никто никогда не напишет), не будет собрана сборщиком мусора — она "утекает" и копится в памяти.

```go
// БАГ:
func leak() {
    ch := make(chan int)
    go func() {
        val := <-ch // ждёт вечно, если ch никто не закроет и не запишет
        fmt.Println(val)
    }()
    // функция leak() завершается, горутина остаётся висеть навсегда
}
```

**Правило:** у каждой запущенной горутины должен быть чёткий и гарантированный путь завершения — через закрытие канала, `context.Context` с отменой, или естественное завершение цикла.

```go
// ИСПРАВЛЕНО — с context:
func noLeak(ctx context.Context) {
    ch := make(chan int)
    go func() {
        select {
        case val := <-ch:
            fmt.Println(val)
        case <-ctx.Done(): // гарантированный выход при отмене
            return
        }
    }()
}
```

## 4. Паттерн Fan-Out / Fan-In

**Fan-out** — раздать работу нескольким горутинам, **fan-in** — собрать результаты обратно в один канал.

```go
func fanOut(input <-chan int, n int) []<-chan int {
    outputs := make([]<-chan int, n)
    for i := 0; i < n; i++ {
        out := make(chan int)
        outputs[i] = out
        go func() {
            defer close(out)
            for v := range input {
                out <- v * v
            }
        }()
    }
    return outputs
}

func fanIn(channels ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    wg.Add(len(channels))

    for _, ch := range channels {
        go func(c <-chan int) {
            defer wg.Done()
            for v := range c {
                out <- v
            }
        }(ch)
    }

    go func() {
        wg.Wait()
        close(out) // закрываем ТОЛЬКО после того, как все источники исчерпаны
    }()

    return out
}
```

## 5. Ограничение количества одновременных горутин (semaphore через буферизованный канал)

Когда нужно ограничить конкурентность (например, не более 10 одновременных HTTP-запросов к внешнему API):

```go
sem := make(chan struct{}, 10) // "семафор" ёмкостью 10

for _, url := range urls {
    sem <- struct{}{} // занимаем "слот" — блокируется, если все 10 заняты
    go func(u string) {
        defer func() { <-sem }() // освобождаем слот
        fetch(u)
    }(url)
}
```

## 6. errgroup — удобная обёртка над WaitGroup с обработкой ошибок

Из полу-стандартной библиотеки `golang.org/x/sync/errgroup` — очень частый практический инструмент:

```go
import "golang.org/x/sync/errgroup"

var g errgroup.Group

for _, url := range urls {
    url := url // важно для Go < 1.22, см. конспект 3
    g.Go(func() error {
        return fetch(url) // если хоть одна вернёт ошибку — она будет доступна после Wait
    })
}

if err := g.Wait(); err != nil {
    fmt.Println("одна из горутин завершилась с ошибкой:", err)
}
```
