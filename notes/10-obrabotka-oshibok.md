# Конспект 10. Обработка ошибок

## 1. Философия: ошибки — это значения, а не исключения

В Go нет `try/catch`. Ошибка — это обычное значение типа `error`, которое функция возвращает **последним** параметром по конвенции. Вызывающий код обязан явно проверить её.

```go
type error interface {
    Error() string
}
```

Это встроенный интерфейс из одного метода. Любой тип с методом `Error() string` автоматически является `error`.

```go
func divide(a, b float64) (float64, error) {
    if b == 0 {
        return 0, errors.New("деление на ноль")
    }
    return a / b, nil
}

result, err := divide(10, 0)
if err != nil {
    fmt.Println("Ошибка:", err)
    return
}
fmt.Println("Результат:", result)
```

**Почему так, а не исключения:** явная проверка на каждом уровне делает поток ошибок видимым прямо в коде — не нужно "угадывать", какая функция может бросить исключение и какого типа. Цена — больше строк кода с `if err != nil`, что многие новички поначалу считают многословным, но со временем это становится привычным и предсказуемым стилем.

## 2. Создание ошибок

```go
import (
    "errors"
    "fmt"
)

err1 := errors.New("простая ошибка")
err2 := fmt.Errorf("не удалось обработать пользователя %d", userID) // с форматированием
```

## 3. Кастомные типы ошибок

Когда нужно передать структурированную информацию об ошибке (не только текст):

```go
type NotFoundError struct {
    ID int
}

func (e *NotFoundError) Error() string {
    return fmt.Sprintf("пользователь с id=%d не найден", e.ID)
}

func getUser(id int) (*User, error) {
    if id == 0 {
        return nil, &NotFoundError{ID: id}
    }
    return &User{}, nil
}
```

## 4. Оборачивание ошибок (error wrapping) — %w и errors.Is/As

При передаче ошибки вверх по стеку вызовов часто хочется добавить контекст, не потеряв исходную ошибку. Для этого используется глагол `%w` в `fmt.Errorf`:

```go
func loadConfig() error {
    _, err := os.Open("config.yaml")
    if err != nil {
        return fmt.Errorf("не удалось загрузить конфиг: %w", err) // оборачиваем, не теряя оригинал
    }
    return nil
}

err := loadConfig()
fmt.Println(err) // "не удалось загрузить конфиг: open config.yaml: no such file or directory"

// errors.Is — проверка: "является ли эта ошибка (или что-то, что она оборачивает) конкретной ошибкой?"
if errors.Is(err, os.ErrNotExist) {
    fmt.Println("файл действительно не существует")
}

// errors.As — "достать" конкретный ТИП ошибки из цепочки оборачиваний
var notFoundErr *NotFoundError
if errors.As(err, &notFoundErr) {
    fmt.Println("ID не найденного пользователя:", notFoundErr.ID)
}
```

**Разница между Is и As (частый вопрос на собеседовании):**
- `errors.Is(err, target)` — сравнивает по **значению**, отвечает на вопрос "это конкретно вот эта ошибка (например, sentinel-ошибка вроде `sql.ErrNoRows`)?"
- `errors.As(err, &target)` — сравнивает по **типу**, отвечает на вопрос "есть ли в цепочке ошибка вот такого типа?" и, если да, кладёт её в `target`.

### Sentinel-ошибки (заранее объявленные переменные-ошибки)

```go
var ErrNotFound = errors.New("не найдено")

func find() error {
    return fmt.Errorf("поиск не удался: %w", ErrNotFound)
}

if errors.Is(find(), ErrNotFound) {
    fmt.Println("совпало, несмотря на обёртку")
}
```

## 5. panic и recover

`panic` — экстренное прерывание нормального потока выполнения (аналог необрабатываемого исключения). Используется **только** для действительно неожиданных ситуаций (баг в программе, недопустимое состояние), а не для обычных ошибок бизнес-логики (для них — `error`).

```go
func mustPositive(n int) {
    if n < 0 {
        panic("число не может быть отрицательным")
    }
}
```

**Когда panic оправдан:**
- Ошибка программиста, а не пользователя (например, выход индекса за границы слайса — сама среда выполнения паникует).
- Невозможность продолжить работу программы в принципе (например, не удалось загрузить обязательный конфиг при старте).

**recover** — перехватывает панику и позволяет продолжить выполнение. Работает **только** внутри `defer`:

```go
func safeCall() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("восстановились после паники:", r)
        }
    }()
    panic("что-то пошло не так")
}

safeCall()
fmt.Println("программа продолжает работать") // выполнится, паника не убила программу
```

Частый практический пример — middleware в HTTP-сервере, которое перехватывает панику в одном запросе, чтобы не "уронить" весь сервер:

```go
func recoveryMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if err := recover(); err != nil {
                log.Println("восстановились после паники:", err)
                http.Error(w, "внутренняя ошибка сервера", http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r)
    })
}
```

## 6. Правила хорошего тона при работе с ошибками

1. Никогда не игнорируй ошибку молча (`_, _ = someFunc()`) без явного комментария, почему это безопасно.
2. Добавляй контекст при оборачивании (`fmt.Errorf("контекст: %w", err)`), а не просто пробрасывай ошибку без изменений — это упрощает отладку по логам.
3. Не используй `panic` для валидации пользовательского ввода — только `error`.
4. Не злоупотребляй `recover` — "проглатывание" паник без логирования маскирует реальные баги.
