# Конспект 19. Идиомы Go, инструменты, code review checklist

## 1. gofmt — единый стиль форматирования для всех

Go — один из немногих языков, где форматирование кода полностью автоматизировано и не обсуждается в команде (в отличие от бесконечных споров "табы или пробелы" в других языках):

```bash
gofmt -l .          # список файлов, которые НЕ отформатированы по стандарту
gofmt -w .           # переформатировать файлы на месте
go fmt ./...          # то же самое, обёртка над gofmt для всего модуля
```

Большинство редакторов (VS Code, GoLand) запускают `gofmt` автоматически при сохранении файла. Ключевая идея: единый стиль во всём Go-сообществе означает, что чужой код выглядит знакомо, а code review не тратится на споры про отступы.

## 2. goimports — форматирование + автоматическое управление импортами

```bash
goimports -w .
```

Дополнительно к форматированию удаляет неиспользуемые импорты и добавляет недостающие, сортирует их по группам (стандартная библиотека / внешние пакеты).

## 3. go vet — статический анализ подозрительного кода

```bash
go vet ./...
```

Находит вещи, которые технически компилируются, но почти наверняка являются багом: неправильные форматные строки в `Printf` (`%d` для строки), недостижимый код, некорректное использование мьютексов после копирования и т.д.

## 4. golangci-lint — агрегатор линтеров (стандарт индустрии)

Объединяет десятки линтеров в одном инструменте, настраивается через `.golangci.yml`, обязателен в CI большинства серьёзных Go-проектов:

```bash
golangci-lint run ./...
```

Типичные линтеры внутри: `errcheck` (непроверенные ошибки), `unused` (неиспользуемый код), `gosimple` (упрощение конструкций), `staticcheck` (более глубокий статический анализ).

## 5. Ключевые идиомы Go (то, что отличает "Go-код" от "кода на Go")

### Ранний возврат вместо вложенных if (guard clauses)

```go
// НЕidiomatично — глубокая вложенность:
func process(user *User) error {
    if user != nil {
        if user.Age >= 18 {
            if user.Verified {
                return doSomething(user)
            } else {
                return errors.New("не верифицирован")
            }
        } else {
            return errors.New("несовершеннолетний")
        }
    } else {
        return errors.New("пользователь не задан")
    }
}

// Идиоматично — ранние возвраты, минимальная вложенность:
func process(user *User) error {
    if user == nil {
        return errors.New("пользователь не задан")
    }
    if user.Age < 18 {
        return errors.New("несовершеннолетний")
    }
    if !user.Verified {
        return errors.New("не верифицирован")
    }
    return doSomething(user)
}
```

### Маленькие интерфейсы, определённые там, где используются

В Go принято объявлять интерфейс **в пакете-потребителе**, а не в пакете-реализации (обратное тому, что интуитивно кажется правильным в языках с классами):

```go
// В пакете service (потребитель) — определяем то, что нам НУЖНО:
type Storage interface {
    Save(data []byte) error
}

// В пакете postgres (реализация) — просто структура с методом,
// НЕ знающая о существовании интерфейса Storage:
type PostgresStorage struct{}
func (p *PostgresStorage) Save(data []byte) error { /* ... */ return nil }
```

### Не использовать голые указатели там, где хватит значения

Возвращать структуру по значению, если она маленькая и неизменяемая, вместо `*Struct` — меньше нагрузки на сборщик мусора (данные остаются на стеке, а не "убегают" в кучу).

### Названия переменных — короче в маленькой области видимости

```go
for i, v := range items { ... }   // нормально — короткая область видимости, всё понятно из контекста
// но:
func CalculateMonthlyRevenueForActiveSubscribers(...) { ... } // на уровне пакета — имя должно быть самодостаточным
```

Правило по мотивам официального "Effective Go": чем шире область видимости переменной/функции, тем более описательным должно быть её имя.

## 6. Code review checklist (что реально проверяют в PR на Go-проектах)

1. **Обработка ошибок** — нет ли проигнорированных `err`, есть ли контекст при оборачивании (`%w`).
2. **Утечки ресурсов** — закрыты ли файлы/соединения/`resp.Body` через `defer`.
3. **Конкурентность** — нет ли доступа к разделяемым данным без мьютекса, нет ли утечек горутин.
4. **Указатели vs значения** — консистентны ли receiver'ы у методов одного типа.
5. **Тесты** — покрыты ли новые ветки логики, особенно граничные случаи (nil, пустой слайс, ноль).
6. **Экспортируемое API** — действительно ли нужно делать функцию/поле экспортируемым, или можно спрятать реализацию.
7. **Использование контекста** — прокидывается ли `context.Context` через цепочку вызовов, где может понадобиться отмена/таймаут.
8. **Магические числа/строки** — вынесены ли в именованные константы.
